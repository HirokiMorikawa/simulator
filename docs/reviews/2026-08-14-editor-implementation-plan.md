## 1. 背景

### 1.1 出発点の質問

「UI で自由に物体・環境を編集し、複雑なシナリオを組んで検証できる状態にしたい」
——[01-vision.md](../00-foundation/01-vision.md) が「検証して遊べるシミュレータ」として
最初から掲げているゴールの、まだ手の付いていない側面である。

vision §1 は「検証」と「遊ぶ」をこう定義する:

> **検証**: 再現された現象が現実(解析解・実測値・保存則)と一致するかを**ユーザー自身が
> 確かめられる**こと。
> **遊ぶ**: パラメータを変え、**物を配置し**、何が起きるかを試せること。

物理エンジン本体はこの定義を満たしている(7ドメイン、644テスト、解析解1%以内、決定論
ビット一致)。満たしていないのは「ユーザー自身が」「物を配置し」の部分——エディタ UI 側である。

### 1.2 実測した現状

12領域について「ソルバが持つ種別数 / シーンJSONが書ける数 / UIから作れる数」を数えると:

| | ソルバ | シーンJSON | UIから作れる |
|---|---|---|---|
| 合計 | 51 | 46 | **9** |

シーンJSONはソルバの90%に追随しているのに、UIは18%で止まる。結合は14種すべてが
JSONにあるのにUIからは1つも作れない。**物理は完成しており、欠けているのは配線だけ**。

決定的な事実がいくつかある(詳細は architecture-proposal.html 参照):

- `export_scene_json`(`crates/sim-wasm/src/lib.rs:2181`)は `format!` による手書きで、
  bodies の3形状しか書き出せない。joints・couplings・fluids・thermal・circuit・probes は
  無言で脱落する。**編集したシーンを保存できない。**
- `Scenario` の55構造体(`crates/sim-world/src/scenario.rs`)はすべて `Deserialize` のみで、
  `World` から書き戻す型が存在しない。
- 形状の表現が4つある(`Shape` / `ShapeJson` / TypeScript の独自パーサ / `sim-render` の
  `Primitive`)。互いに手で同期させる契約で、同期を強制する仕組みが無い。`ShapeJson` は
  `Capsule` を受け付けるが TypeScript 側は3種のままのため、**カプセルを含むシーンは
  0.3m の球として描かれる**(出荷済み43シーンが未使用のため現時点では未発現)。
- ワークスペースに残る `todo!()` は4箇所、すべて Compound / ConvexMesh
  (`crates/sim-mechanics/src/shape.rs:55,111`、`collision.rs:91,1157`)。この2形状は
  型としてしか存在せず、質量を訊くと panic する。
- 回路だけは例外的に自由配線エディタに到達している(素子は3/7種のみだが、
  「種別＋ノード＋値」という一般形で作られている)。この形が、他ドメインへ広げるべき
  正解のかたち。

### 1.3 中心的な判断

真実の所在を `World`(ソルバの生状態)から**シーンドキュメント**へ移す。`World` は
そこから毎回コンパイルされる導出物にする。理由:

1. `from_scenario`(`Scenario → World`)は既に純粋関数として存在する。コンパイラは
   作らなくてよい。欠けているのは逆写像(`Serialize` + `World → Scenario`)だけ。
2. `World: Clone` + `snapshot()/restore()` が既にあり、Timeline が1秒ごとに丸ごと
   複製している。「作り直しが安い」はこのコードベースで既に実証済みの性質。
3. 決定論と整合する——同じドキュメントは同じ `World` を生み、同じ `state_hash` になる。
   保存が「手元のドキュメントを書き出すだけ」になり、脱落が構造的に起こらなくなる。

境界の引き方: **トポロジーを変える編集(ボディ・ジョイント・結合・領域の追加削除)は
再構築、状態を変える編集(位置・速度・質量・スイッチ)は既存の `Command` 経路**。

wasm 境界は機能ごとの専用メソッド(現在118本・2,798行)をやめ、`schema()` / `read()` /
`apply()` の3本へ畳む。serde が既に構造体を記述しているのでスキーマ生成はほぼ機械作業。
Inspector のフォームはスキーマから自動生成し、Rust に Desc を1つ定義すれば UI に
編集欄が生える状態にする。

### 1.4 進め方

層ごとの積み上げではなく、**全層を薄く貫く縦串**を1本ずつ通す。積み上げ式は
下2層が終わるまで誰も価値を確認できず、判断を誤っても分からないため。

最初の縦串をジョイント(＝車の組み立て)にするのは、ジョイントが**他のボディを参照する**
ため安定IDの導入から逃げられず、かつ物理側(`WheelJoint`・`BallJoint`・`HingeMotorPd`)が
既に実装・検証済みで、純粋に土台だけを試せるため。合格判定も明快になる:
「UIで車を組み立てて、保存して、読み直したら D24 と同じ挙動になる」。

`todo!()` 4箇所の穴埋めをこの縦串に合流させたのは、車体を単一の箱ではなく Compound
として組めば、①の合格判定がそのまま Compound の受け入れ試験になるため。

## 3. 意図的にやらないこと

- 物理コア(7ドメイン・644テスト)には触れない。
- 汎用ECSやプラグイン機構は作らない。要るのはドキュメントとスキーマだけ。
- Unity の機能パリティは目標にしない。目標は「複雑なシナリオを組んで検証できる」こと。
- 造形(3D CAD のスケッチ・押し出し・ブーリアン)は本リストの対象外。凸分解が必須になり
  「外部クレート実質ゼロ」の方針では自前実装が要る——物理1ドメイン分の仕事になるため、
  縦串⑤(飛行機)が実際に不便を感じてから改めて判断する。
