Target architecture

最終成果物像 — シーンドキュメントを中心に据えた統合エディタ

物体と環境を自由に編集し、複雑なシナリオを組んで検証できる状態。到達点を6枚の図で示します。中心にある一つの判断は、真実の所在をソルバの状態からシーンドキュメントへ移すこと。他はすべてその帰結です。

01いま何が起きていて、何に変えるのか

現状はソルバの状態（World）が真実で、UIはそこを直接読み書きします。書き出しは World を覗いて手書きの文字列で再構成するため、表現できないものが黙って落ちます。完成後はドキュメントが真実で、World はそこから毎回コンパイルされる導出物になります。保存は手元のドキュメントを書き出すだけになり、脱落が起こりようがなくなります。

02編集はどこへ行くのか

ドキュメントが真実になると「編集のたびに World を作り直すのか」という問いが立ちます。答えは半分だけ「はい」で、境界は都合ではなく原則で引きます。その値が World の構築時にしか読まれないなら再構築、実行中に意味を持つ値なら Command。後者はリプレイと決定論の記録に載ります。

03編集欄はどこから生えるのか

いま機能を1つ足すには sim-wasm に専用メソッドを1本、TypeScript にフォームを1枚書きます。すでに公開メソッドは118本・2,798行。ジョイント7種と結合15種を同じやり方で足したら破綻します。だから境界を schema() / read() / apply() の3つに畳み、Inspector のフォームをスキーマから生成します。

04検証はどう回るのか

「複雑なシナリオを検証できる」の中身です。合格基準をシーンに書けるようにし、パラメータを振って何通りも走らせ、結果を重ねて比べる。決定論がビット単位で保証されているエンジンなので、何を変えたら何が変わったかを厳密に切り分けられる——これは Unity には無い、このエンジン固有の強みです。

05画面としての完成像

パネルの骨格は既に Unity 風に揃っていて、操作性はQAで28項目すべて通っています。変わるのは中身の通り方です。下図の色つきの箇所が今回作る部分になります。

ただし Scene View は器としても不完全です。描けるのは球・箱・平面の3種だけで、カプセルはスポーンパレット経由の固定寸法のときしか描かれず、Compound と ConvexMesh には生成コードがありません。しかも ShapeJson は増分Lで Capsule を受け付けるようになったのに TypeScript 側の型は3種のままなので、カプセルを含むシーンを読み込むと物理は正しく動くのに画面には直径0.6mの球が出ます。出荷済み43シーンがカプセルを使っていないため、今日はまだ誰も踏んでいないだけです。

06形状 ── 描画の穴の下に、物理の穴がある

形状が描けないのは表層でした。Shape は6種に育っていますが、ワークスペースに残る todo!() は4箇所で、その4箇所すべてが Compound と ConvexMesh です。AABB・接触生成・体積・慣性のどれも未実装で、質量を訊いた瞬間に panic します。つまりこの2種は型としてしか存在しない。

さらに、形状の表現は engine の中に4つあり、どれも Shape から導出されていません。シーンJSONの ShapeJson、TypeScript の独自パーサ、そしてパストレーサの Primitive。sim-render は sim-mechanics に依存すらしていないので、パストレーサが物理シーンを描く経路は存在しません（D40–D43 はシーンを手で組んでいます）。

07全ドメインが同じ形をしている

形状だけの話ではありません。全ドメインを「ソルバが持つ種別数 / シーンJSONが書ける数 / UIから作れる数」で並べると、どの領域も同じ形をしています。シーンJSONはソルバによく追随していて（結合は14種すべて）、落ちているのは常にUIの側です。

電子回路だけが例外的に進んでいます。ノード数を決めて任意のトポロジーを組める本物の自由配線エディタがあり、組んだ回路をMNAが解いて解析解と厳密一致することがPlaywrightで検証済みです。ただし素子は抵抗・電圧源・スイッチの3種だけ。皮肉なことに、D19「電気工作台」自身がコンデンサとダイオードを使っているので、そのD19をUIで組み直すことはできません。

08造形（3D CAD）をどこに置くか

造形はこのエンジンでは飾りになりません。質量を形状の体積 × 材料密度から算出するので、造形すると本物の質量と慣性テンソルが出ます。「アルミの翼を鋼で作り直したら重心が動いて失速特性が変わる」が実験できる——これは 01-vision.md の「現実の写像」そのものです。

ただし判断が要る点が一つ。造形の結果をドキュメントにレシピ（操作列）で持つか、ベイクした凸片で持つか。レシピだけを持つと読み込みのたびにカーネルを再実行することになり、数値的に脆いブーリアンが決定論の経路に入ります。両方を持ち、境界をドキュメントの内側に引くのが答えです。

段階は4つに分かれ、価値の大半は前半にあります。⓪ todo!() 4箇所を埋める（これ抜きでは何も動かない）→ ① Compound を UI で組む（部品の配置・スナップ・対称ミラー。カーネル不要でここまでで実用性の8割）→ ② スケッチと押し出し → ③ ブーリアン。

②以降は正直に重い。凸でない形は GJK/EPA が扱えないので凸分解が必ず挟まり、「外部クレートは実質ゼロ」という本プロジェクトの方針を踏まえると自前実装になります。物理ソルバ1ドメイン分の仕事で、勢いで入る領域ではありません。翼型を手で数値指定して不便を感じたときが、着手すべき時期の合図です。

10どの順で到達するか

層ごとに積み上げず、全層を薄く貫く縦串を1本ずつ通します。積み上げ式だと下2層が終わるまで誰も価値を確認できず、判断を誤っても分かりません。最初の縦串をジョイント（＝車の組み立て）にするのは、それが他のボディを参照するため、安定IDから逃げられなくなるからです。合格判定も明快になります——「UIで車を組み立てて、保存して、読み直したら D24 と同じ挙動になる」。

11最初の一手

挙動を一切変えない変更から入ります。図4の下段——2本のCIゲートを、いま必ず落ちるテストとして置く。あわせて、コード中に262箇所ある自己申告された「縮約」を機械集計する監査スクリプトを足す。チェックボックスが隠していた総和を可視化するためです。

ここが緑になる道筋に合意できたら、そのまま図9の縦串①（ジョイント＝車の組み立て）に進みます。既存の物理ソルバには触りません——644本のテストと解析解1%以内という資産は、この作業でリスクに晒す場所ではない。todo!() 4箇所を埋めるのは空白を埋める作業であって、既存の振る舞いを変える作業ではないので、この線引きの内側に収まります。
